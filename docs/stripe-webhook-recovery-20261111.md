# November 11 live webhook recovery

Stripe endpoint `we_1Ree4PJRsCJh7NlTMyje89wU` returned ten HTTP 503 responses beginning November 8. Four events remained unsuccessful: two subscription updates and two paid invoices across two subscriptions.

Account-bound checkout writes `customer_entitlements`, while the older webhook processor required a row in `subscriptions`. A properly paid renewal therefore failed with `existing_mapping_required` even though its customer, user, subscription and original checkout had already been verified. The webhook store now falls back only to a unique, live, non-QA, account-bound entitlement. It preserves the original checkout binding and still refreshes subscription/invoice evidence from Stripe before applying the atomic, replay-protected update. Ambiguous, conflicting or missing managed bindings still fail closed. No email matching is introduced.

The second subscription predates app-account checkout: its original Stripe checkout, current subscription metadata and old database row contain no user ID. It cannot safely become an app entitlement automatically. For these specific existing legacy rows, the handler rechecks the original paid live checkout and exact customer/subscription IDs, then stores an immutable review receipt before acknowledging delivery. A receipt records that reconciliation is needed, not that access was granted. Provider/storage failures still return 503. The review table has RLS enabled, no public/member privileges and service-only SELECT/INSERT. The linter's no-policy informational notice is intentional for service-only storage.

Validation: 46 inherited webhook/SQL tests and seven targeted renewal/legacy/QA checks passed. These cover raw signature validation, replay conflicts, atomic updates, account isolation, paid periods, duplicate review events, ambiguous/mismatched fallback bindings and retriable storage/provider failures. Production schema privileges were checked independently. Production build and actual failed-event resends are verified separately during release.

Recovery uses the pinned official Stripe CLI and the application's existing production credential in its own build environment. The explicit script verifies account and endpoint, resends only the four inspected event IDs, and never prints provider bodies or credentials. It does not create payments, modify subscriptions, issue refunds, or alter endpoint event subscriptions. It is not part of the normal build command.
